# Hardware Stratified Protocol

## Purpose

This experiment collects the hardware trajectories used to train and evaluate the data-driven dynamics model in `ddm_ablation`. The protocol is stratified so that the dataset contains:

1. shaker-only excitation for identifying the disturbance channel;
2. voice-coil-only excitation for identifying the actuator channel;
3. simultaneous shaker and voice-coil excitation for identifying coupled two-input dynamics.

The output of this experiment is a fixed set of `300` hardware trajectories saved as CSV files. These files are later consumed directly by `ddm_ablation`.

## Protocol Blocks

The protocol plan is generated by `utils.signals.build_protocol_plan` and saved to:

```text
data/protocol_plan.csv
```

The default plan seed is:

```text
20260516
```

The plan contains:

| Block | Count | Purpose | Shaker signal | Voice-coil signal |
|---|---:|---|---|---|
| B1 | 75 | shaker disturbance channel | multisine, chirp, mixed | zero |
| B2 | 75 | voice-coil actuation path | zero | multisine, chirp, PRBS, mixed |
| B3 | 150 | coupled two-input dynamics | multisine, chirp, mixed | multisine, chirp, PRBS, mixed |

The generated plan is balanced by construction:

```text
B1 shaker: 25 multisine, 25 chirp, 25 mixed
B2 voice: 19 multisine, 19 chirp, 19 PRBS, 18 mixed
B3 shaker: 50 multisine, 50 chirp, 50 mixed
B3 voice: 38 multisine, 38 chirp, 37 PRBS, 37 mixed
```

Chirp direction alternates globally between `up` and `down` whenever a trajectory uses a chirp component. Non-chirp trajectories use `chirp_direction = none`.

## Duration And Sampling

The protocol constants come from `utils.signals`:

```text
dt = 0.03 s
duration = 6.0 s
steps = 200
```

Each saved trajectory therefore has exactly `200` rows. A saved trajectory is considered valid only if it has `200` rows, contains a `time` column, and has a positive trajectory index in the first row.

## Signal Families

The generated signals are bounded force commands.

Global limits:

```text
shaker force limit = +/- 9 N
voice-coil force limit = +/- 2 N
shaker voltage range = +/- 3 V
conversion = 3 N per signed volt
```

The shaker force is converted to DAQ voltage by:

```text
shaker_voltage = clip(shaker_force / 3, -3, 3)
```

The voice-coil force is sent through `quiet_put_voice_coil_force`, which clips the requested force to `+/- 2 N` and converts the magnitude to the Arduino command code used by the hardware interface.

The signal families are:

- `multisine`: sum of `1` to `4` sine waves. Each tone has random frequency in `0.2-5.0 Hz`, random phase, and random amplitude between `0.1` and `1.0` times the channel force limit.
- `chirp`: linear frequency sweep over `0.2-5.0 Hz`, with balanced `up` and `down` directions across the protocol.
- `PRBS`: random piecewise-constant values from `20` evenly spaced force levels, held for `1` to `20` samples. PRBS is used only for the voice-coil channel.
- `mixed`: weighted sum of the allowed signal families for that channel. For shaker, mixed means multisine plus chirp components. For voice coil, mixed can include multisine, chirp, and PRBS.

After generation, any signal that exceeds its channel limit is uniformly scaled back to the valid range.

All nonzero shaker trajectories use a raised-cosine start/stop envelope with a `0.5 s` ramp. Therefore the shaker command is exactly `0 N` at the first sample and returns to `0 N` at the end. The voice-coil command is not smoothed by this envelope, because PRBS-like actuator excitation is intentionally included.

## Hardware Collection Loop

Each trajectory is collected by `collect_one_trajectory` in `main.py`.

For every trajectory:

1. Generate shaker force, shaker voltage, and voice-coil force from the fixed protocol item seed.
2. Stop shaker and voice-coil outputs.
3. Clear the x/y sensor and Arduino serial buffers.
4. Wait briefly after flushing.
5. Sample approximately `2.0 s` of settled hardware data.
6. Use the settled mean displacement as the zero offset.
7. Run a `200`-sample real-time loop at nominal `dt = 0.03 s`.
8. Read raw `x/y` displacement from the serial sensors.
9. Subtract the zero offset.
10. Reconstruct filtered displacement, velocity, and acceleration online.
11. Write the shaker voltage to the DAQ task.
12. Write the voice-coil force to the Arduino task.
13. Save all measured states, commands, timing, and protocol metadata.

The script starts the DAQ task once before the loop and writes the shaker voltage with `auto_start=False`. The actual sample interval is saved as `dt_sample`, so later analysis can use the measured timing rather than assuming a perfectly constant clock.

## Online Kinematic Filtering

The measured raw displacements are processed by `OnlineKinematicsFilter`:

1. Apply a causal first-order low-pass filter to displacement.
2. Compute velocity from finite differences of filtered displacement using the measured timestamp interval.
3. Apply the same causal low-pass filter to velocity.
4. Compute acceleration from finite differences of filtered velocity.
5. Apply the same causal low-pass filter to acceleration.

The cutoff is:

```text
cutoff_hz = 8.0
```

Both raw displacements and filtered kinematics are saved in every trajectory CSV.

## Safety, Restart, And Resume Behavior

Before each trajectory, `prepare_hardware_for_trial` stops outputs and clears serial buffers. After each successful or aborted attempt, `finish_hardware_trial` stops outputs again, clears buffers, and waits:

```text
post_wait_s = 2.0
```

The hardware is also reset once before collecting the first missing trajectory in a resumed run.

The main abort condition is an adjacent-sample displacement jump:

```text
JUMP_ABORT_M = 0.008 m
```

If either raw displacement channel jumps by more than this value between adjacent samples, the current attempt is aborted and restarted. The default maximum number of attempts per trajectory is:

```text
max_retries = 20
```

Re-running `main.py` is safe. Existing valid `trajectory_XXX.csv` files are skipped, so collection resumes from the first missing or invalid trajectory.

## Saved CSV Schema

Each successful trajectory is saved as:

```text
data/trajectory_XXX.csv
```

Each row contains:

```text
index
total
block
purpose
shaker_type
voice_type
chirp_direction
sample
duration_s
dt_nominal
steps
seed
cutoff_hz
time
timestamp_abs
dt_sample
x1_raw

x1_filtered
v1_filtered
a1_filtered
x2_filtered
v2_filtered
a2_filtered
shaker_force_n
shaker_voltage_v

```

The protocol plan is fixed once written. If `data/protocol_plan.csv` already exists and matches the expected duration and step count, the script reuses it rather than regenerating it.

## Plotting

`plot.py` creates a compact preview figure:

```text
figures/hardware_protocol_preview.pdf
```

The preview selects up to six trajectory files while trying to include different blocks. Each row of the preview shows:

```text
x1/x2 displacement
v1/v2 velocity
a1/a2 acceleration
shaker and voice-coil force commands
```

The preview is diagnostic only. The training and evaluation pipeline uses the saved CSV trajectories directly.

## Outputs

Core files:

- `main.py`: hardware collection with restart and resume support.
- `plot.py`: preview plotting from saved trajectories.
- `test_from_76.py`: local debugging helper for continuing from trajectory 76.

Generated files:

- `data/protocol_plan.csv`: fixed 300-trajectory protocol plan.
- `data/trajectory_001.csv` through `data/trajectory_300.csv`: collected hardware trajectories.
- `data/hardware_runtime_debug.log`: optional debug log, mainly used around trajectory 76.
- `figures/hardware_protocol_preview.pdf`: preview figure.

## Commands

Collect or resume the full hardware protocol:

```bash
python main.py
```

Collect with a custom retry limit:

```bash
python main.py --max-retries 30
```

Create the preview figure:

```bash
python plot.py
```

## Link To DDM Ablation

`ddm_ablation` loads these trajectories as the source dataset. For each trajectory, it uses:

```text
state = [x1_filtered, v1_filtered, x2_filtered, v2_filtered]
action = voice_force_n
disturbance = shaker_force_n
```

This is why the protocol deliberately includes shaker-only, actuator-only, and coupled two-input excitation. The DDM needs enough variation to learn both independent channels and their coupled response under simultaneous excitation.
